`tourney-api` is the backend for [tourney.social](https://tourney.social). One Go
modular monolith serves the JSON API, the RBAC auth and the live score stream.

It is the authority on permissions and on every rule about scores, scheduling and
draws. The web app mirrors some of those rules to keep the UI honest, but it
cannot grant anything the API refuses.

## Features

- **Three draw formats** — single elimination, round robin, and group→knockout,
  each generated by a pure function with no database or HTTP in the way.
- **Tennis-accurate scoring** — per-set scores, plus walkover, retired and
  cancelled as first-class match states rather than notes on a result.
- **Scheduling that cannot double-book** — a `btree_gist` exclusion constraint
  makes one court in two places at once impossible at the database level, not
  merely unlikely.
- **Live scores over SSE** — no WebSocket, no Redis, no polling.
- **Role-based access** — `super_admin` and `organizer`, enforced per route
  group and again by row-level security in Postgres.
- **Timezone-correct** — every timestamp stored in UTC, rendered in the
  tournament's own IANA zone.
- **OpenAPI 3.1 as the contract** — the frontend's TypeScript types are
  generated from it.
- **Free-tier shaped** — sized to run on Supabase Free and a single Fly machine.

## Architecture

```
                    ┌──────────────┐   SSE    ┌────────────────┐
   spectators ─────►│              │◄─────────│  realtime hub  │
                    │              │          │  (in-process)  │
   organizers ─────►│  Gin router  │          └────────────────┘
                    │   /api/v1    │                  ▲
   super admin ────►│              │──────────────────┘
                    └──────┬───────┘  publish on score change
                           │
        ┌──────────────────┼──────────────────┐
        ▼                  ▼                  ▼
   auth · tournament · event · participant · draw
   match · schedule · audit · platform          (internal/*)
        │
        ▼
   pgxpool ──► PostgreSQL  (RLS, exclusion constraints, goose migrations)
```

Each module under `internal/` owns a `handler.go` (HTTP), `service.go` (rules)
and `repository.go` (SQL). Wiring is plain constructor calls in
`cmd/api/main.go` — there is no DI container, so the dependency graph is
readable top to bottom.

**Stack:** Go 1.25, Gin, pgx/v5, sqlc, goose, slog, PostgreSQL.

## Getting started

### Prerequisites

| | |
| --- | --- |
| [Go 1.25+](https://go.dev/dl/) | If you keep several Go versions installed, put the one you want first on `PATH`. |
| PostgreSQL | Supabase works, so does local Postgres via the included `docker-compose.yml`. |

Two optional CLIs, needed only for `make sqlc` and `make migrate-create`.
Applying migrations does **not** need them — `make migrate-up` uses the runner
embedded in the binary:

```sh
go install github.com/sqlc-dev/sqlc/cmd/sqlc@latest
go install github.com/pressly/goose/v3/cmd/goose@latest
```

### Quick start

```sh
git clone git@github.com:muslimalfatih/tourney-api.git
cd tourney-api
cp .env.example .env
```

Fill in `DATABASE_URL`, `MIGRATION_DATABASE_URL` and `JWT_SECRET`. For local
Postgres instead of Supabase:

```sh
docker compose up -d
# then point both URLs at:
#   postgresql://tourney:tourney@localhost:5432/tourney?sslmode=disable
```

Then:

```sh
make migrate-up   # apply the schema
make seed         # create the first super admin from SEED_ADMIN_* in .env
make run          # serve on :8080
```

Check that it came up:

```sh
curl localhost:8080/healthz   # {"status":"ok"}
curl localhost:8080/readyz    # {"status":"ready"} once the database answers
```

Sign in:

```sh
curl -s localhost:8080/api/v1/auth/login \
  -H 'content-type: application/json' \
  -d '{"email":"admin@example.com","password":"change-me-please"}'
```

### Make targets

`make help` lists them all.

| Target | What it does |
| --- | --- |
| `run` / `build` | Run the server, or build to `./bin/api` |
| `migrate-up` / `migrate-down` / `migrate-status` | Apply, roll back, inspect migrations |
| `migrate-create name=add_foo` | New goose migration (needs the goose CLI) |
| `sqlc` | Regenerate typed Go from `db/queries` (needs the sqlc CLI) |
| `seed` | Create the initial super admin, demo org and Renon Cup demo data |
| `fmt` / `vet` / `tidy` | Housekeeping |
| `test` / `test-integration` | See [Testing](#testing) |

## Configuration

All configuration is read from the environment once at startup; a validation
failure is fatal, so the process never runs half-configured
(`internal/config/config.go`).

| Variable | Default | Notes |
| --- | --- | --- |
| `APP_ENV` | `development` | `production` switches Gin to release mode |
| `PORT` | `8080` | |
| `LOG_LEVEL` | `info` | slog level |
| `DATABASE_URL` | — | **Required.** Runtime connection (Supabase: transaction pooler, `:6543`) |
| `MIGRATION_DATABASE_URL` | falls back to `DATABASE_URL` | Migrations only (Supabase: session pooler, `:5432`) |
| `DB_MAX_CONNS` | `8` | Per machine — keep small on the free tier |
| `JWT_SECRET` | — | **Required**, minimum 16 characters. `openssl rand -base64 48` |
| `ACCESS_TOKEN_TTL` | `15m` | |
| `REFRESH_TOKEN_TTL` | `720h` | 30 days |
| `CORS_ORIGINS` | `http://localhost:5173` | Comma-separated allowlist |
| `SEED_ADMIN_EMAIL` / `_PASSWORD` / `_NAME` | — | Used by `make seed` only |

## Connecting to Supabase

The free tier gives you a small budget of direct connections, so the two URLs in
`.env` point at different endpoints on purpose.

`DATABASE_URL` is the runtime connection and uses the transaction pooler on port
6543. Keep `DB_MAX_CONNS` small: the limit applies per machine, and a second
machine doubles the real usage.

`MIGRATION_DATABASE_URL` is the migration connection and uses the session pooler
on port 5432, because goose needs session features the transaction pooler drops.

Both are pgbouncer, which cannot see prepared statements the way a direct
connection can. The pool therefore sets
`DefaultQueryExecMode = pgx.QueryExecModeSimpleProtocol`
(`internal/storage/postgres/db.go`). Without it, queries fail with
`prepared statement already exists (SQLSTATE 42P05)`. If you ever point this
service at a direct connection, that line is safe to leave in place.

## Project layout

```
cmd/
  api/            server entrypoint: load config, wire modules, serve
  migrate/        goose runner with the migrations embedded
  seed/           first super admin, demo org, and the Renon Cup demo data
  cleanup/        archives or restores a fixed, fingerprinted list of dev-data rows
internal/
  config/         environment-based configuration
  server/         Gin engine, router, middleware, JSON envelope and errors
  auth/           login, JWT, argon2id, RBAC
  tournament/     tournaments and their lifecycle
  event/          divisions within a tournament, and public slugs
  participant/    entries and seeding
  draw/           the format generators — pure, database-free
  match/          scoring rules and match state
  schedule/       courts and time slots
  realtime/       the SSE hub
  audit/          the audit trail
  platform/       super-admin surface
  storage/        pgxpool and the sqlc-generated queries
  inttest/        integration tests that run against a real database
db/
  migrations/     goose SQL, embedded with //go:embed
  queries/        sqlc sources
api/openapi.yaml  the contract
```

## API

Everything sits under `/api/v1`. Health probes (`/healthz`, `/readyz`) sit
outside it so platform checks hit stable paths.

### Authorization

| Prefix | Who can call it |
| --- | --- |
| `/api/v1/public/*` | anyone, no token — read models plus the SSE stream |
| `/api/v1/auth/*`, `/api/v1/me` | anyone, for sign-in and session refresh |
| organizer routes | a token with the `organizer` or `super_admin` role |
| `/api/v1/admin/*` | a token with the `super_admin` role |

Access tokens live 15 minutes and refresh tokens 30 days, both configurable.

### Response envelope

```jsonc
// one record:  { "data": { ... } }
// a list:      { "data": [ ... ], "meta": { "page", "per_page", "total" } }
// a failure:   { "error": { "code", "message", "details?" } }
```

Validation failures return **422** with a machine-readable `code` and a
`details` object. Conflicts — two matches booked on one court at the same time,
a fixture that already exists — return **409** the same way.

> [!IMPORTANT]
> The web app reads `code` and supplies its own wording. Changing a message
> string is safe; changing a code is a breaking change.

## Database

Eleven goose migrations, applied in order. The later ones are worth knowing
about, because each moves a rule out of application code and into the database:

| Migration | What it does |
| --- | --- |
| `00004_enable_rls` | Turns on row-level security |
| `00009_scoring` | Per-set scores; walkover, retired and cancelled become real match states |
| `00010_schedule_conflicts` | The `btree_gist` exclusion constraint that makes a double-booked court impossible |
| `00011_tournament_timezone` | An IANA timezone per tournament — stored UTC, rendered local |

Core enums: `user_role`, `org_status`, `tournament_status`, `event_discipline`,
`event_format` (`single_elim` · `round_robin` · `group_knockout`), `event_gender`,
`pairing_mode`, `stage_kind`, `match_status`.

## Testing

```sh
make test              # unit tests — pure logic, no database
make test-integration  # DB-backed tests under internal/inttest
```

`test-integration` needs a real database in `TEST_DATABASE_URL` or
`DATABASE_URL`, with migrations already applied. It covers security boundaries,
scoring, scheduling conflicts, timezone handling, duplicate fixtures, typed
slots and score corrections.

Browser tests live in the sibling `tourney-e2e` workspace.

## Deployment

The service runs on [Fly.io](https://fly.io) as the app `tourney-api`, built
from the `Dockerfile` and configured by `fly.toml`.
[`.github/workflows/fly-deploy.yml`](.github/workflows/fly-deploy.yml) deploys on
push.

Set the secrets before the first deploy, or the release fails:

```sh
fly secrets set DATABASE_URL=... MIGRATION_DATABASE_URL=... JWT_SECRET=... CORS_ORIGINS=...
```

Fly runs `/app/migrate up` in a one-off machine before the new release takes
traffic, so schema changes ship with the code that needs them.

> [!WARNING]
> **Deploy with `--ha=false` and keep the machine count at 1.**
> The realtime hub holds subscribers in process, so a second machine would take
> half the spectators and never tell them about the scores published on the
> other one. Live updates would fail quietly, for some viewers only — the
> hardest kind of bug to notice. Horizontal scaling needs Redis pub/sub first.

The machine suspends when idle but never stops, because a spectator opening a
live scoreboard should not wait for a cold start.

## Contributing

Issues and pull requests are welcome.

1. Fork the repository and create a branch off `main`.
2. Make your change. Keep handler / service / repository responsibilities where
   they are, and keep the draw generators pure.
3. Run `make fmt vet test` before you push. If your change touches SQL or
   scheduling, run `make test-integration` too.
4. If you change the HTTP surface, update [`api/openapi.yaml`](api/openapi.yaml)
   in the same commit — the frontend's types are generated from it.
5. Open a pull request describing what changed and why.

New error responses need a new `code`, not a reworded message. New rules that
can be expressed as a database constraint belong in a migration.
